# v2.2.2 Starlink VLAN telemetry repair

On October 22, PCS v2.2.1 had an active collector but unavailable telemetry on
its commissioned VLAN WAN. A device-bound TCP connection to the fixed dish
endpoint succeeded; the collector failed earlier with `ModuleNotFoundError:
No module named 'dbus'` while validating the NetworkManager VLAN identity.
Debian's system interpreter could validate the same interface and retrieve a
sanitized `CONNECTED` status with current measurements.

The installer now explicitly requires `python3-dbus`, repairs the existing venv
with system package visibility and verifies imports before replacing helpers.
Pinned RPC dependencies and private Starlink configuration are preserved.
Exact VLAN identity validation and device-bound transport are unchanged.

## Validation

- Starlink unit tests cover exact VLAN resolver delegation and rejection.
- A disposable Debian environment reproduces the missing D-Bus import, executes
  the actual installer provisioning section, verifies all imports, repeats that
  section and checks package consistency. Hosted CI runs this alongside the
  existing five jobs and their full software/integration checks.
- Appliance preflight self-test passed all enabled checks. The boot-time
  NetworkManager wait unit had previously timed out; a fresh `nm-online -s`
  completed successfully. This historical boot wait did not block dish access.
- Final live deployment results, exact commits and CI runs are recorded in the
  GitHub release and the workspace deployment report.

This repair does not establish current-topology cold-boot, Mini restart,
failover, RF, or physical recovery acceptance. No Mini power action is part of
the repair or its regression tests.
