# PCS bandwidth manager

An opt-in Pi-native bandwidth subsystem for the PCS client LAN. The Nokia Beacon
6 can remain an AP/switch; it is not involved in enforcement. The Pi must be the
client gateway. This does **not** create guest isolation, stop IP spoofing, or
turn rate limits into a monthly data allowance.

## Install and administration

Install dependencies and run from the reviewed PCS checkout:

```bash
sudo apt-get install nftables iproute2 python3-yaml
sudo bash scripts/setup-pcs-bandwidth.sh --install
sudo pcs-bandwidth status
```

The installer enables `pcs-bandwidth.service`. A fresh configuration selects
`unrestricted`, so installation alone does not cap Internet traffic. Existing
configuration is preserved. Review `/etc/pcs/bandwidth.yaml` before selecting a
metered profile. The usual control-panel service must run the updated
`web/pcs-control-panel/pcs_control_panel.py` to display **Bandwidth settings**.
Deploying/restarting that live service is a separate operational step.

The authenticated admin panel links to `/admin/bandwidth`. Its compact page offers:

- Per-profile network upload/download ceilings and default per-client limits.
- Manual activation of Starlink, cellular, or unrestricted policy.
- IPv4 client overrides, names, trusted unlimited exceptions, and return to defaults.
- Active state, configuration warnings, and per-client byte counters.

Form changes require the existing administrator session and CSRF token. A revision
check rejects stale browser changes instead of overwriting newer settings. The
root helper accepts only fixed `web-status`/`web-update` commands with bounded,
validated JSON on stdin. No arbitrary command or config path is accepted through
the web helper. Client details are not added to the public status endpoint.

```bash
sudo pcs-bandwidth profile starlink
sudo pcs-bandwidth client 10.42.0.232 --name Andrew-Laptop --down 25M --up 10M
sudo pcs-bandwidth client 10.42.0.20 --unlimited
sudo pcs-bandwidth client 10.42.0.20 --remove
sudo pcs-bandwidth status --json
sudo pcs-bandwidth reload
sudo pcs-bandwidth profile unrestricted
```

`client` replaces that IP's override; omitted rates use profile defaults. Rates
accept `M`, `mbit`, `mbps`, `kbit`, etc., between 1 kbit/s and 10 Gbit/s. Bits,
not bytes, are used. A trusted exception bypasses its **individual** ceiling,
but remains inside the aggregate ceiling. Overrides apply across all enabled
profiles. `unrestricted` removes shaping and accounting resources completely.

## Configuration and separation of responsibilities

See [the complete example](../config/bandwidth.example.yaml). Configuration parsing
and policy validation live in `pcs_bandwidth_config.py`, topology and Linux
enforcement in `pcs_bandwidth_engine.py`, and CLI/service/JSON control in
`pcs_bandwidth.py`. A future UI or discovery worker should use this same validated
control boundary; it must not independently invoke tc or edit firewall rules.

`lan_network` supports one IPv4 /24 through /30. Each usable non-router address
gets its own default class and counters, even before that client is discovered.
Two unknown devices therefore do not share a single default cap. DHCP/MAC
discovery, temporary boosts, usage budgets, persistent accounting, and IPv6
shaping remain future work. Names and explicit trust are configured manually.

LAN detection requires one interface with an address in the LAN subnet. WAN
detection selects the lowest-metric main-table default route. Equal-cost routes,
policy routing, or ambiguous LANs require explicit `lan_interface` and/or
`wan_interface`. Multipath WAN is not automatically supported. The service
reconciles interface changes every ten seconds, retaining the manually selected
profile; it does not start cellular or choose a profile automatically. No WAN
means `WAITING_FOR_WAN` with normal unshaped connectivity.

IPv6 is left untouched and always reported as unshaped/unaccounted, including
whether global IPv6 addresses are present. IPv6 clients can bypass IPv4 limits.
The subsystem does not disable IPv6 or modify forwarding settings.

Network ceilings cover the aggregate of forwarded IPv4 client traffic. Internet
traffic generated by the Pi itself (for example operating-system updates) is not
included in this v1 client policy. Local services and management remain separate.

## NAT-safe packet path and ownership

The original WAN-ingress diagram needs adjustment on a NAT gateway: downloaded
packets there still carry the router's translated destination, not the client IP.
This implementation classifies **forwarded** IPv4 packets after routing/DNAT,
then redirects at egress into dedicated IFBs. Linux IFB supports returning an
egress-redirected packet to its original output interface; see the
[kernel IFB implementation](https://github.com/torvalds/linux/blob/master/drivers/net/ifb.c)
and [tc mirred documentation](https://man7.org/linux/man-pages/man8/tc-mirred.8.html).

```text
Upload:   LAN -> forward classification -> SNAT -> WAN egress -> pcsbw-up -> WAN
Download: WAN -> DNAT -> forward classification -> LAN egress -> pcsbw-down -> LAN
```

The dedicated `inet pcs_bandwidth` table has an accept-policy forward chain at
priority 100. Rules match both input/output interfaces and the client IPv4, and
exclude the LAN subnet on the opposite side. They count bytes/packets and assign
skb priority (tc class ID). They never set routing/conntrack marks or alter
firewall verdicts, NAT, DHCP, DNS, or routing. Forwarded traffic to another
network through the selected WAN is considered WAN use, including upstream
private networks. Services on PCS itself do not traverse this chain.

Reserved resources:

| Resource | Ownership |
| --- | --- |
| nft table `inet pcs_bandwidth` | Comment `pcs-bandwidth-v1` |
| IFBs `pcsbw-up`, `pcsbw-down` | Interface alias `pcs-bandwidth-v1` |
| HTB majors `b701:`, `b702:` | Exist only on manager IFBs |
| clsact egress preference `47801`, basic handle `1` | Exact redirect to manager IFB |
| Runtime journal and lock | Root-only `/run/pcs-bandwidth` |

HTB aggregate parents contain one class per client with an fq_codel leaf. Rates
above the aggregate ceiling are clamped to it. Guaranteed shares sum to no more
than the aggregate and unused capacity can be borrowed up to each ceiling.
Without an aggregate ceiling the parent uses a 10 Gbit/s implementation maximum.
Default root queues on physical WAN/LAN interfaces are preserved. Existing
clsact is shared; a conflicting ingress qdisc or reserved filter causes refusal.
Other subsystems must not reuse these class IDs/skb priorities or reserved names.
Flowtable/hardware forwarding offload must not bypass the forward hook; v1 does
not support such offloaded traffic.

## Lifecycle, failure behavior, and counters

`apply` and `reload` are idempotent: an unchanged, healthy policy preserves its
counters. Changed policies briefly detach/rebuild shaping and reset counters.
Queues may lose in-flight packets during changes; established connections remain
routable. Policy changes favor continued unshaped connectivity over blocking.
Counters measure forwarded IPv4 bytes before shaping, including packets that may
later be dropped; they are not carrier billing records. Stopping, rebooting, or
changing policy can reset them. Persistent accounting can later consume the
versioned JSON status without changing the engine.

The service reconciles missing resources and has `ExecStopPost` cleanup even
after an abnormal exit. No user-space daemon handles packets. Until systemd
cleanup runs, existing kernel shaping can remain active after a process crash;
it does not add a forwarding dependency. Cleanup removes classification and
redirects before IFBs and deletes an owned clsact only if neither direction has
any remaining filters. Foreign objects are not deleted. There is no global
`nft flush ruleset`, root qdisc replacement, or interface down operation.

## Troubleshooting and removal

```bash
sudo pcs-bandwidth validate
sudo pcs-bandwidth plan                  # inspect proposed kernel configuration
sudo pcs-bandwidth status --json
sudo journalctl -u pcs-bandwidth -n 80 --no-pager
sudo nft list table inet pcs_bandwidth
sudo tc -s class show dev pcsbw-down
sudo tc -s qdisc show dev pcsbw-up
sudo tc filter show dev eth0 egress
```

Missing IFB, HTB, fq_codel, basic/em_meta, or mirred kernel support produces an
error and cleanup. A reported ownership conflict requires inspection; do not
delete another subsystem's queues to force installation. Invalid configuration
does not authorize an arbitrary shell command. Use `systemctl stop` to stop the
daemon; a standalone `pcs-bandwidth stop` is cleanup only and a running daemon
will reapply its policy on the next pass.

```bash
sudo pcs-bandwidth profile unrestricted  # persistent bypass
sudo systemctl disable --now pcs-bandwidth.service
sudo bash scripts/setup-pcs-bandwidth.sh --remove
# Optional, only when its saved policy is no longer wanted:
sudo rm /etc/pcs/bandwidth.yaml
```

## Acceptance procedure

Automated Linux tests use only temporary namespaces, veth links, a bridge and
synthetic WAN NAT. Run on a disposable Linux machine:

```bash
sudo apt-get install nftables iproute2 iperf3 python3-yaml
sudo python3 tests/integration_bandwidth.py --run
python3 -m unittest discover -s tests -p 'test_pcs_bandwidth.py' -v
python3 -m unittest discover -s tests -p 'test_pcs_control_panel.py' -v
```

For actual PCS acceptance, use two LAN clients and an authorized external iperf3
server. WAN throughput tests consume data; choose their duration deliberately.
Keep an independent management connection and record the selected profile first.

1. Start `iperf3 -s` on PCS for a local baseline. From a LAN client run
   `iperf3 -c 10.42.0.1 -t 10` and its `-R` counterpart. Apply a 5M/2M client cap
   and repeat. Local throughput should remain close to baseline, not 5/2 Mbps.
   Local traffic must not change that client's WAN counters.
2. Against your external server run `iperf3 -c SERVER -t 10 -R` and
   `iperf3 -c SERVER -t 10`. Expect roughly 5 Mbps download and 2 Mbps upload,
   allowing protocol overhead and link conditions.
3. Set client B to 25M/10M. Test both independently and concurrently using
   separate server ports. Verify their independent caps and combined network
   ceilings. Remove B's override and verify its individual default limits.
4. Set A unlimited and verify it can exceed its old individual cap while still
   respecting the aggregate. Check separate RX/TX counters for both clients.
5. Switch Starlink to unrestricted. Verify limits disappear, both manager IFBs
   and the dedicated nft table disappear, and unrelated firewall tables remain.
6. With a shaping profile selected, stop the service. Confirm Internet routing
   and local services continue. Start it again and confirm policy restoration.
7. During an approved reboot window, reboot PCS and confirm the service restores
   its saved profile. Test a WAN disconnect/reconnect only in an approved network
   maintenance window; absence should be reported without breaking LAN services.
8. Check admin login/CSRF protection and IPv6 warning. Verify a stale second
   browser tab cannot overwrite a newer policy. Confirm the page matches CLI
   status after every successful change.

Disposable tests do not establish physical Wi-Fi throughput, Pi CPU headroom,
live WAN behavior, metered usage accuracy, or reboot acceptance on PCS.
