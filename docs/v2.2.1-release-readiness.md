## Verified implementation delta from v2.2.0

The [draft changelog](../CHANGELOG.md) describes only the unpublished delta:
separate public/admin atomic snapshots; singleton collection; subprocess-group
timeout cleanup; explicit loading/stale states and optional API freshness;
collection batching/memoization; corrected Internet and self-test detection;
systemd credential/cache access for SNMP; and conservative physical-assisted
startup with modem readiness. VLAN migration, SNMP polling itself, bandwidth
controls and bounded APRS beep suppression already shipped in v2.2.0.

Snapshots use a ten-second target loop interval, but the public and admin
collections run sequentially; this is not a guarantee of a new sample every ten
seconds. Reads become stale after 45 seconds and never trigger collection. The
public page refreshes every ten seconds and the HTTP cache lasts one second.

## Recorded validation before maintenance

- The [October 10–11 commissioning record](dashboard-snapshot-commissioning.md)
  reports 185 combined Linux tests, with five later focused route self-test
  regressions. These are not described as full candidate CI.
- Recorded HTTP responses were around 0.24 seconds; admin background collection
  remained approximately 7–9 seconds, above the earlier three-second target.
- Physical port mapping and limited IPv4 HTTP/SNMP management isolation were
  verified; polling and steady-state startup diagnostics were checked. The final
  self-test had no failures and an expected uncommitted-checkout warning.
- The separate Android task recorded 15 JVM tests, lint, debug/minified release
  builds and signature verification. These do not establish real-phone acceptance.

New maintenance validation and exact local commit IDs are recorded in the
workspace's `PCS-UNATTENDED-MAINTENANCE-REPORT.md`, outside the release source.

## Open release and acceptance gates

Recovery development now provides a [tested inactive preparation workflow](recovery-staging.md)
on a separate local branch. It preserves the existing live restore behavior and
does not establish current VLAN reinstall acceptance. Its manifest changes affect
future exports and must be reviewed as part of the exact chosen release head.

- Review the exact candidate and choose whether Android v0.3.0 is included.
- Run the full hosted CI on the reviewed head when publication is authorized;
  local results are not a GitHub Actions result.
- Resolve or explicitly document the [recovery coverage gaps](recovery-coverage.md).
  Do not claim current VLAN wipe/reinstall acceptance from the v1.9.7 result.
- Reconcile installed hashes, source and backups before any later deployment.
- Complete no-preferred-WAN cold boot, actual Mini startup, cellular Internet and
  sustained preferred-WAN recovery with an independent control/recovery path.
- Complete broader physical isolation/persistence, GNSS reacquisition, routed
  throughput/bandwidth policy and appropriate radio acceptance.
- Adapt the fail-closed qualification harness for VLANs before running current
  FQ-301/FQ-302/FQ-303. Historical legacy results stay valid within their scope.
- Exercise Android upgrade, trust/token retention, revocation, layout and network
  paths on a real phone. Review certificate renewal and biometric compatibility.
- Obtain explicit release authorization before any push, PR, merge, tag or release.

The candidate preserves 240-second startup grace when physical state is connected
or unknown, existing failure/recovery timing and operator-session protection.
Nothing in this preparation authorizes a reboot, WAN fault, RF transmission,
cellular-data trial, hardware power test or appliance configuration change.
